# www.xedur.com

Source code for [www.xedur.com](https://www.xedur.com/), the code portfolio of Eetu Rantanen (XeduR). Most projects are Solar2D games and tools that run in the browser as embedded HTML5 builds.

The site is hosted on GitHub Pages and generated by a custom Python static page builder.

## Project structure

│   ├── nav.js                  # Navbar scroll and mobile toggle

## Building

Run the build script from the `tools/` directory:

```bash
python update_website.py            # incremental build
python update_website.py min        # incremental build, minified HTML
python update_website.py force      # full rebuild, ignoring the skip cache
python update_website.py min force  # full minified rebuild (either arg order)
```

The committed site is built with `min`. A plain run rewrites every page and `js/*.js` unminified.

### What it generates

| Output | Source |
|--------|--------|
| `index.html` | `frontpage.html` template + the category manifests and demo front matter |
| `404.html` | `404.html` template + every valid path, for fuzzy URL matching |
| `sitemap.xml` | Every valid page path, with lastmod dates kept in `tools/components/data/sitemap_dates.json` |
| `llms.txt` | `tools/components/data/llms.json` + the category manifests |
| `demo/index.html` | `demo-index.html` template (a noindex list of all demos) |
| `demo/<folder>/index.html` | `demo.html` template + the demo's `tools/demos/<folder>.md` |
| `demo/<folder>/app/index.html` | `iframe.html` template (Solar2D app loader) |
| `tangents/<slug>/index.html` | `tangents-post.html` template + `tools/tangents/<slug>.md` |
| `tangents/` and `tangents/<n>/` | `tangents-list.html` template (paginated index, 10 per page) |
| `tangents/tag/<slug>/` | `tangents-list.html` template (per tag, paginated) |
| `tangents/feed.xml` | Atom 1.0 feed of the newest posts |
| `tangents/<slug>/<slug>-social.png` | Auto-generated 1200x630 social card (unless `socialImage` names a custom file) |
| `tangents/tangents-social.png` | Generic social card for the index, pagination, and tag pages |
| `img/xedur-social.png` | Frontpage social card, shared by the 404 page |
| `demo/<folder>/<folder>-social.png` | Social card for each demo page, standalone pages included |
| `js/*.js` | Copied from `tools/js/` (minified with `min`) |

Apart from the generated social cards listed above, the build never touches `img/` or `fonts/`, and in `demo/<folder>/` it writes only the pages and the card, never the hand-managed screenshots, app binaries, or assets. CSS lives in `tools/css/styles.css` and is inlined into every page, so there is no root `css/` folder. A sitemap entry gets today's date only when its page's content changed. A demo page also gets today's date when its app files change (`demo/<folder>/app/`; for a standalone page, `demo/<folder>/` and `tools/standalone/<folder>/`, minus the generated page and social card), compared by a content hash kept in `sitemap_dates.json`, so a fresh clone or a touched file never moves a date.

### Incremental builds and caching

The builder regenerates only what changed and prunes output that no longer has a source.

- Per-item pages (each demo page, each Tangents post, and each copied `js/*.js`) are skipped when none of their sources changed.
- Each demo's app loader is generated every run, so a Solar2D build's own `index.html` copied into `demo/<folder>/app/` is replaced with the loader.
- Change detection hashes each source file's bytes rather than reading modification times, so a fresh `git clone` does not force a rebuild.
- Aggregate pages (`index.html`, `demo/index.html`, the Tangents list and tag pages, the feed, `404.html`, `sitemap.xml`, `llms.txt`) are regenerated every run. A byte-identical result is never written, so repeated runs cause no git churn.
- A change to `base.html`, `navbar.html`, the navbar logo `img/xedur-code-portfolio.png`, `footer.html`, `tools/css/styles.css`, `update_website.py`, or `markdown_engine.py` rebuilds every per-item page, because each of them affects every page.
- Switching between normal and `min` output also rebuilds every page.
- A generated page whose source is gone (a deleted demo `.md`, a dropped manifest entry, a deleted post, a pagination page that no longer exists) is deleted, along with its now-empty directory.
- Pruning only ever deletes paths that match a known generated-output pattern. Any other stale cache entry is logged as a warning and left alone, so a corrupted cache can never remove a manual asset such as `img/`, demo thumbnails, app binaries, or a custom `socialImage` file.
- `force` rebuilds every page regardless of the cache, while pruning keeps working.

The cache lives at `tools/.build_cache.json` (gitignored). Deleting it triggers one full rebuild with byte-identical output, and a corrupt cache is treated as absent. It also keeps each demo asset's size and modification time, so only changed assets are re-hashed for the sitemap check.

### Build log

Every run writes a report to `tools/build_logs/build_log_<YYYY-MM-DD_HH-MM-SS>.txt` (gitignored): the mode, whether it was forced, the counts of files written, skipped, and pruned, and the lists of errors, warnings, written files, and pruned paths. Only the newest 30 logs are kept.

## Adding and updating projects

Each project is a markdown file at `tools/demos/<stem>.md` whose stem is listed in one of the category manifests: `tools/demos/games.json`, `solar2d.json`, or `other.json`.

A manifest holds:

- `sectionTitle` and `sectionDescription` for the homepage section.
- `sectionIndex`, the two-digit number shown beside the section heading.
- An optional `"band": true`, which puts the section on the alternating full-bleed background.
- `demos`, the ordered list of stems; that order is the display order on the homepage.

The Roso Games and Contact sections are not manifests, so the Roso number (02) and band live in `frontpage.html` and the Contact number (05) is `contactSectionIndex` in `frontpage.json`.

The file stem is the demo identity. For regular and standalone demos it must equal the front-matter `folder` and the `demo/<folder>/` directory. For external links it is any unique kebab-case id.

Front matter is a flat `key: value` block between `---` fences. It cannot nest, so SEO overrides are individual keys rather than an `seo` object.

### Entry types

The build decides the type from the front matter, in this order:

1. Has `externalUrl`: an external link.
2. Has `type: standalone`: a standalone project.
3. Otherwise: a regular demo.

**Regular demo**: a Solar2D HTML5 build that runs in an iframe.

```
---
title: The Dark
folder: the-dark
descriptionShort: Card description shown on the homepage.
tech: Solar2D, Lua
ogTitle: XeduR - The Dark
ogDescription: Description for social media shares.
metaDescription: Custom meta description.
---
The long description in markdown: paragraphs, **bold**, *italic*, `- ` lists, `## ` subheadings, and `[text](url)` links.

**How to play:**

- Controls go here.

[[github url="https://github.com/XeduR/..."]]
```

- The card thumbnail is `demo/<folder>/<folder>-small.jpg` and the `.bin` name is detected from `demo/<folder>/app/`, so neither needs a key.
- `tech`, `ogTitle`, `ogDescription`, `metaDescription`, and `ogImageAlt` are optional.
- A paragraph that is only bold text ending in a colon (`**How to play:**`) renders as a gold label for the content below it.
- The body ends with `[[github url="..."]]` for the public repo panel, or a bare `[[github]]` for the private-source panel.
- Generates `demo/<folder>/index.html` and `demo/<folder>/app/index.html`.

**External link**: a homepage card that opens another site in a new tab. No pages are generated.

```
---
title: Solar2D Playground
externalUrl: https://www.solar2dplayground.com/
image: img/external/solar2d-playground.jpg
descriptionShort: Card description.
tech: HTML5, CSS3, JavaScript
---
```

`image` is required because there is no `folder` to derive a thumbnail from, and there is no body.

**Standalone project**: a custom HTML/JS page in the site's chrome instead of an iframe-loaded app. Only the Pseudorandom Number Generator uses it.

```
---
title: Pseudorandom Number Generator
folder: pseudorandom-number-generator
type: standalone
descriptionShort: Card description.
tech: HTML5, CSS3, JavaScript, Lua
---
```

There is no body: the page comes from `tools/standalone/<folder>/`, and only `demo/<folder>/index.html` is generated.

| File | Required | Purpose |
|------|----------|---------|
| `content.html` | Yes | The page body, inserted into the base template |
| `config.json` | Yes | Page metadata: `title`, `metaDescription`, `metaKeywords`, optional `seo` |
| `head.html` | No | Extra `<head>` tags for the project's own CSS and JS |

### Adding a regular demo

1. Build the Solar2D project for HTML5 and run `html5_build_patcher.py` on the build folder (see below).
2. Put the build files (`.bin`, `.data`, and the rest) in `demo/<folder>/app/`.
3. Add `<folder>-small.jpg` and `<folder>-large.jpg` to `demo/<folder>/`.
4. Create `tools/demos/<folder>.md` and add `<folder>` to the right category manifest.
5. Run the build.

### Adding a standalone project

1. Create `tools/standalone/<folder>/` with `content.html`, `config.json`, and optionally `head.html`. End `content.html`'s outer `<div class="content after-header">` with a `{{contactSection}}` line for the contact panel.
2. Add `<folder>-small.jpg` and `<folder>-large.jpg` to `demo/<folder>/`, plus any CSS or JS in `demo/<folder>/css/` and `demo/<folder>/js/`, referenced from `head.html` with the `{{basePath}}` prefix.
3. Create `tools/demos/<folder>.md` with `type: standalone` and add `<folder>` to the manifest.
4. Run the build.

### Adding an external link

1. Create `tools/demos/<stem>.md` with `externalUrl` and `image` (usually `img/external/<name>.jpg`), and add `<stem>` to the right category manifest.
2. Run the build.

### Patching HTML5 builds

Run `html5_build_patcher.py` on every new Solar2D HTML5 build before copying it into `demo/<folder>/app/`:

```bash
python html5_build_patcher.py path/to/build/folder
```

It patches the `.bin` and the generated `index.html`:

- Removes the blur callback that freezes the app when the user clicks outside it.
- Removes the `alert()` from `printErr` that pops up on non-fatal WASM errors.
- Deletes the unused `index-debug.html` and `index-nosplash.html`.

### SEO overrides

A regular demo's meta description defaults to `descriptionShort`, and its social tags default to `ogTitle` = `XeduR - <title>`, `ogDescription` = `descriptionShort`, and `ogImageAlt` = `XeduR - <title>`. Override any of them with front-matter keys:

```
metaDescription: Custom meta description.
ogTitle: Title for social media shares
ogDescription: Description for social media shares
ogImageAlt: Alt text for the preview image
```

`ogImage` is the demo's generated social card (see Social share images). Keywords fall back to the site-wide defaults.

## Tangents (writing system)

Tangents is the markdown-written writing section at `/tangents/`: paginated list pages, per-tag pages, post pages, and an Atom feed. Posts live in `tools/tangents/<slug>.md`, where the file stem is the slug and the URL is `/tangents/<slug>/`. Slugs are lowercase kebab-case (`[a-z0-9-]`) and not all digits; an invalid slug is a build error.

### Writing a post

1. Copy `tools/components/templates/new-tangent-post.md` to `tools/tangents/<slug>.md`, fill in the front matter, and write the markdown body.
2. Commit any post images into `tangents/<slug>/` and reference them with `[[image src="foo.png" ...]]`; paths resolve relative to the post URL.
3. Run the build.

[`tools/TANGENTS.md`](tools/TANGENTS.md) is the authoring guide: every front matter key, markdown feature, and directive (images, YouTube videos, repository panels, empty lines, callout boxes), with examples, plus what is not supported.

### Dates

Publish dates and body hashes live in `tools/components/data/tangents_dates.json`, which is committed because publish dates cannot be re-derived. A post is published on its first build, or on its `published` date. Without an `updated` key, the updated date is the day the rendered body last changed, so editing `summary`, `tags`, or `title` alone does not bump it. An `updated` key overrides that date. Either shows as "Updated:" only when it is later than the publish date. Dates render as `13 July 2026`.

An unreadable `tangents_dates.json` stops the build instead of being overwritten; restore it from git. An unreadable `sitemap_dates.json` only warns and restarts every lastmod. Post pages do not depend on the dates file, so after editing it by hand, run a `force` build.

### Feature images and missing images

A post's `featureImage` sits in an invisible 16:9 frame above the body, scaled to fit without cropping or a visible box around it, and the build puts a horizontal divider between it and the body. On list pages it becomes a thumbnail beside the row that links to the post like the title does. A relative path resolves against the post URL, so list pages rewrite it to reach the post folder.

An image that fails to load, whether a feature image or an `[[image]]`, is swapped for a striped "Image unavailable" panel showing its alt text, by `js/image-fallback.js`. That script loads only on pages with images. A relative or root-relative image whose file is missing from the repo also logs a build warning; remote images are not checked at build time. A local file name whose letter case differs from the file's counts as missing, because GitHub Pages is case-sensitive. An `[[image]]` without `width` and `height` gets its local file's size written in at build time, so the page does not shift while it loads.

### Pagination, tags, feed

The tag chips on list pages come with a "Sort by" menu (most or fewest tangents, A to Z, Z to A), a case-insensitive substring search, and a "Clear all" button that resets both and returns to the first index page, all from `js/tag-filter.js`. The choice is kept in `sessionStorage`, so it carries over to tag and pagination pages in the same tab. The current page's tag always stays visible. Without JavaScript the chips show most-used first.

Post pages link the neighbouring posts as "Previous:" and "Next:", each limited to 46% of the column width.

List pages hold 10 posts, newest first (`/tangents/`, `/tangents/2/`, and so on). Every list page ends with a pagination bar: "Newer posts" and "Older posts" links, faded at either end of the range, around a "Page N out of TOTAL" field. `js/page-jump.js` jumps to the typed page on Enter or when the field loses focus, clamps numbers past the last page to it, and restores the current number for anything that is not a positive integer. Each tag gets its own paginated set at `/tangents/tag/<slug>/`. Two tag spellings that slugify to the same value (`Solar2D` and `solar2d`) are a build error. The feed at `/tangents/feed.xml` carries the newest 20 posts and is linked from every post, list, and tag page.

### YouTube consent

`[[youtube]]` renders a thumbnail placeholder, not an iframe. `js/video-consent.js`, loaded only on pages that need it, swaps in a `youtube-nocookie.com` iframe after the visitor clicks "I accept". Consent is stored in `localStorage` (`videosAccepted`), so the site sets no cookie and requests nothing from `youtube-nocookie.com` before consent. When site storage is blocked, the button still loads the videos, and consent lasts until the page reloads. The thumbnail itself comes from `img.youtube.com` before consent.

### Social share images

Every page shares a branded 1200x630 card: the "XeduR" heading and the X mark at the top, and a band under a hairline at the bottom that names the page.

- Post pages: `tangents/<slug>/<slug>-social.png`, with a "Tangents" label above the post title.
- Tangents index, pagination, and tag pages: one generic card at `tangents/tangents-social.png`.
- Frontpage and 404: `img/xedur-social.png`, with the tagline under the heading and the site address in the band.
- Demo pages, standalone ones included: `demo/<folder>/<folder>-social.png`, with the demo title in the band. External demos have no page and no card.

Colours, fonts, text, sizes, and layout numbers live in `tools/components/data/social_cards.json`. Its text metrics echo `tools/css/styles.css` (display tracking, label tracking, and each echoed element's line-height), and `tools/tests/test_social_cards.py` fails when the two drift apart.

A demo or standalone page whose card is missing falls back to the frontpage card, then to `seo.ogImage` in `frontpage.json`. Its `og:image:alt` is "XeduR - <title>" unless the demo's front matter sets `ogImageAlt`.

The `socialImage` key in a post overrides the default:

- Absent or `auto`: generate the card.
- `<filename>`: use the committed `tangents/<slug>/<filename>` as is; 1200x630 is recommended. The page declares no `og:image:width`/`height` for it. A missing file warns and falls back to the generated card.
- `<slug>-social.png`, the generated name in any letter case, is a build error.

Generated cards are committed. A card regenerates only when the generator script, its kind and text, `social_cards.json`, or the logo and font assets change, tracked in `tools/components/data/social_images.json`. Deleting a post or demo prunes its generated card; a custom `socialImage` file is never pruned.

Rendering needs [Pillow](https://python-pillow.github.io/), which is imported only when a card actually renders, so an up-to-date build never loads it. A needed render without Pillow fails the build with a clear message. Card text uses the Space Grotesk and Inter files in `tools/components/fonts/`.

The generator also runs on its own while iterating on the card design:

```bash
python generate_social_images.py              # every card: posts, generic, frontpage, demos
python generate_social_images.py force        # regenerate everything (writes only what changed)
python generate_social_images.py <slug> ...   # only the named posts
```

It refreshes the images and the manifest only; run `update_website.py` for the pages.

## Templates

HTML templates live in `tools/components/templates/` and use `{{placeholder}}` tokens that the build replaces. `{{basePath}}` holds the relative path back to the site root (`./` on the homepage, `../../` on demo pages).

| Template | Purpose |
|----------|---------|
| `base.html` | Root HTML document (head, meta tags, favicons, font preloads, navbar, footer) |
| `navbar.html` | Navigation bar (desktop and mobile). `{{navLogo}}` is `img/xedur-code-portfolio.png` embedded as a data URI, so the logo paints with the page's first frame instead of waiting on the browser cache |
| `footer.html` | Page footer |
| `frontpage.html` | Homepage layout (intro, sections, Roso Games, contact) |
| `section.html` | Homepage section with numbered heading, description, and card grid |
| `card.html` | Project card |
| `contact.html` | Contact panel at the bottom of every page except the 404, numbered only on the homepage. The navbar's Contact link scrolls to the page's own panel, and the 404's goes to the homepage's |
| `demo.html` | Demo page (rendered markdown body and the app embed) |
| `demo-index.html` | List of all demos at `demo/` |
| `iframe.html` | Solar2D HTML5 app loader with Zlib decompression and progress bar |
| `repo-panel.html` | Public repository panel (from the `[[github]]` directive) |
| `repo-panel-private.html` | Private-source panel (from a bare `[[github]]`) |
| `tangents-post.html` | Tangents post page |
| `tangents-list.html` | Tangents index and tag pages |
| `tangents-item.html` | One row in a Tangents list |
| `new-tangent-post.md` | Front matter template to copy for a new post (not used by the build) |
| `404.html` | Error page with the valid paths for fuzzy URL matching |
